# Human-editable model template

Use this folder as the starting point for any graph model in the system. It uses
only the Python standard library. Shared graph types, JSON loading, and pipeline
contracts come from the `utils` package.

## Create a model

1. Copy this `_template` folder into the relevant `models` category.
2. Rename the copied folder, using lower-case words separated by underscores.
3. Edit `config.json`. Most model tuning should happen there.
4. Set `property_target` to `edge`, `node`, or `actuator`, and list one or more
   clear names in `output_properties`.
5. In `model.py`, rename `ModelTemplate` and change the formula in the clearly
   marked `HUMAN-EDITABLE SECTION` inside `calculate_edge`, `calculate_node`, or
   `calculate_actuator`.
6. If the shared dataset schema grows, update the relevant class under
   `utils/graph` once rather than redefining it in this model.
7. Run the model before connecting it to the larger system.

For example, a heat-index model could live at
`models/heat_exposure/heat_index/`, with thresholds and weights in its copied
`config.json`.

## Configuration fields

| Field | Purpose |
| --- | --- |
| `model_name` | Stable name included in every result |
| `description` | Plain-language explanation of the model |
| `enabled` | Turns the model on or off |
| `property_target` | Chooses whether every edge, node, or actuator receives the result |
| `output_properties` | Non-empty list of property names stored on each target entity |
| `input_properties` | Earlier properties to consume, or an empty list for the model's default input |
| `parameters` | Calculation weights a human can tune without changing code |


Keep JSON property names and text in double quotes. JSON does not support
comments, so put explanations in `description` or this file.

## Run the example

From the project root:

```powershell
python -m models._template.model
```

By default, the example loads `dataset/tiny_campus_block`. It validates unique
node and edge IDs, edge endpoints, numeric values, booleans, and distances before
calculating results.

The example returns two values for every edge: a distance-based `distance_cost`
and an `accessibility_cost` that applies a fixed penalty to inaccessible
segments. Both values are saved in each edge's `properties`. Dynamic conditions
such as shade can be generated by earlier model stages and selected with
`input_properties`.

The template passes configured inputs to the calculation as a mapping from
property name to value. Its edge/node example formula sums numeric inputs, but a
copied model can combine or reference individual inputs however its domain logic
requires. If the list is empty, the example uses edge distance or node degree.
Actuator inputs may also be strings or `null`.

The selected calculation method must return a mapping containing every name in
`output_properties` exactly once. Edge and node values must be finite numbers.
Actuator values may be finite numbers, non-empty strings, or `null`. For example:

```python
return {
    "distance_cost": base_value * self._parameter("base_weight"),
    "accessibility_cost": 0.0 if edge.accessible else penalty,
}
```

The shared `ModelOutput` reports every generated property directly.
`property_names` preserves the configured order, and `property_values` maps each
property name to its complete target-entity value mapping. `ModelOutput` validates
that the names and mappings agree and every target ID occurs exactly once. It
also validates numeric edge/node values and the broader actuator value types.
The updated graph contains every output so later stages can consume any of them.

## Actuator targets

Actuators expose three runtime properties, initialized when the dataset loads:

| Actuator type | `status` | `wait_time_s` | `recommended_edge` |
| --- | --- | --- | --- |
| `misting_point` | `"off"` | `null` | `null` |
| `traffic_signal` | `null` | Static `default_wait_time_s` | `null` |
| `directional_led` | `"off"` | `null` | `null` |

Misting and LED status may be `"on"` or `"off"`. Signal wait time must stay
within its static minimum and maximum. An LED recommendation may be `null` or one
of that actuator's statically configured `recommended_edges`. These initial
values are derived by the loader; they are not duplicated in `actuators.json`.

For an actuator model, set `property_target` to `"actuator"`, use state names in
`output_properties`, and implement `calculate_actuator()`. The starter method
preserves the configured properties until model-specific control logic replaces
them.

## Pass results to the next model

Every output contains the updated graph. Pass it directly to the next model:

```python
from utils import ModelInput, load_campus_graph

graph = load_campus_graph("dataset/tiny_campus_block")
first_output = first_model.predict(ModelInput(graph=graph))
second_input = first_output.to_model_input()
second_output = second_model.predict(second_input)
```

Set the second model's `input_properties` to any properties produced by earlier
stages. Existing dynamic properties remain on the graph, so later models can use
several earlier results without changing the JSON dataset.

## Save output for debugging

Saving is explicit so normal model runs do not create files unexpectedly:

```python
from utils import ModelInput, load_campus_graph

graph = load_campus_graph("dataset/tiny_campus_block")
output = model.predict(ModelInput(graph=graph))
saved_path = output.save_json("debug/model_output.json")
```

The JSON file contains every generated property and its values, diagnostics, all
nodes, edges, actuators, and every dynamic property accumulated on the graph. Saving to
an existing path replaces that file.
